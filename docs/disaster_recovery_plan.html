1. Scope

In scope: recovery procedures and backup commitments for:

  • The PostgreSQL database (learner records, attempts, sessions, audit logs)
  • Application source code and deployment configuration
  • Customer-uploaded files (working sheet scans, when present)
  • The custom domain and TLS certificates

Out of scope:

  • Render's underlying infrastructure (responsibility of Render Inc.)
  • Third-party services (Anthropic, GitHub, the domain registrar) — covered by their own SLAs
  • End-user devices used to take assessments (covered by the supervising institution)
  • Multi-client architecture and capacity decisions (covered separately; not a DR concern)

2. Current state — free tiers (app: Render / database: Neon)

The platform currently runs on two free-tier services: Render hosts the application layer; Neon Inc. (neon.tech) provides the managed PostgreSQL database. This is appropriate for development and demonstration but not for production cohort deployment. The known limitations:

  • No automated database backups. Neon's free tier does not include automated snapshots or point-in-time recovery (PITR).
  • No database expiry. Unlike Render's own free PostgreSQL (which expires after 44 days), Neon free tier databases persist indefinitely — but remain unsuitable for production due to the absence of PITR.
  • Cold starts. Neon free tier compute suspends after a period of inactivity; the first query after suspension takes 5–10 seconds. Render free web services also spin down after 15 minutes of inactivity, adding ~30 seconds on first request.

RPO (data loss tolerance)Undefined — last manual pg_dump only

Manual pg_dump is taken before any schema migration or destructive operation and stored encrypted in a non-cloud-synced location. This is a stopgap, not a strategy.

3. Target state — paid tiers (app: Render / database: Neon Launch)

Upgrade to paid tiers on both Render (application) and Neon (database) is a condition of any production cohort deployment. The upgrade procedure is documented in scripts/render_upgrade.sh.

Neon Launch (database) provides:

  • Daily automated snapshots with configurable retention
  • Point-in-time recovery (PITR) — restoration to any second within the retention window via the Neon console
  • On-demand logical exports (pg_dump) at any time
  • Always-on compute — no cold starts on paid tiers
  • Branch-based isolation — separate dev/staging branches on the same plan at no extra cost

Render paid tier (application) provides:

  • Always-on web service — no spin-down on first request
  • Automatic Let's Encrypt SSL on custom domains, including wildcards

4. Recovery procedures by scenario

4.1 Corrupted database (data integrity bug, bad migration)

  1. Identify the time of corruption from application logs
  2. Neon console → Project → Branches → select the main branch → Restore → choose point-in-time seconds before corruption
  3. Neon provisions a restored branch; promote it to main or update DATABASE_URL on the Render web service to the restored connection string
  4. Smoke-test; verify data integrity
  5. Delete the corrupted branch after 7-day verification window

4.2 Accidental data deletion (operator error)

  1. Same procedure as 4.1, restoring to a point seconds before the deletion
  2. If only specific records are missing: connect to the PITR-restored Neon branch, extract the affected rows, and re-insert into the live branch (avoids full cutover)

4.3 Full-region Render or Neon outage (infrastructure)

  1. Confirm the outage: Render at status.render.com; Neon at neonstatus.com
  2. If outage exceeds RTO commitment (4 hours): begin failover-to-non-Render procedure (see §7)
  3. If outage is shorter: communicate via prepared client notification template; resume on restoration

4.4 Account-level compromise — Render or Neon (ransomware-relevant)

This is the scenario where platform-side snapshots are no longer trusted because the Render or Neon account itself is suspect. Procedure:

  1. Treat as a ransomware incident — invoke the response checklist in the disaster-recovery skill
  2. Restore from the most recent off-platform encrypted backup (see §5) — this backup is stored outside both the Render and Neon accounts
  3. Provision fresh accounts if necessary; do not re-use any compromised account
  4. Redeploy from a known-clean Git commit (verify against a local clone before pushing)
  5. Rotate all credentials — Render, Neon, GitHub, email — per the response checklist before restoring service

4.5 Source code or repository compromise (GitHub takeover)

  1. Lock the GitHub repository's main branch protection
  2. Identify the last clean commit (compare against a local clone)
  3. Force-push the clean commit; revoke all GitHub PATs and OAuth apps
  4. Rotate Gmail (the password-reset target) before rotating GitHub itself
  5. Render auto-deploys the rotated commit; smoke-test

5. Off-Render backup commitment

The platform commits to maintaining backups outside both the Render account and the Neon account. This addresses the failure mode in which a compromised cloud account renders platform-side snapshots untrustworthy. Without this commitment, the snapshot story collapses under an account-takeover scenario. The off-platform backup is the last line of defence against simultaneous Render + Neon account compromise.
AspectCommitment
CadenceMonthly encrypted pg_dump taken directly from Neon (via DATABASE_URL), stored outside both Render and Neon accounts
StorageEncrypted USB in physical safe + separate-credentials cloud bucket
EncryptionAES-256 symmetric (gpg --symmetric --cipher-algo AES256)
Passphrase storagePassword manager separate from primary credentials
Retention12 monthly backups; older deleted including from version history
VerificationAnnual decrypt + restore to scratch database

Unacceptable storage locations: Dropbox, iCloud, Google Drive, OneDrive, or any cloud-sync folder tied to the developer's primary identity. Compromise of the primary identity reaches into the sync folder.

5.1 Operational implementation (sam-pack)

The commitments above are operationalised by two scripts in scripts/:

ScriptPurposeWhen to run
verify_backup_environment.shPre-flight check — validates required commands, environment variables, backup directory state, backup_log.txt recency, database reachability, and GPG AES-256 capability. Read-only; no side effects.Before each monthly backup
off_render_backup.shMonthly backup runner — pg_dump → GPG AES-256 symmetric encrypt → SHA-256 hash → append entry to backup_log.txt → delete plaintext → rotate encrypted dumps older than 365 days. Supports --dry-run, --keep-plaintext, and --rotate-only flags.First Monday of every month

Required environment variables: DATABASE_URL (production Render Postgres) and BACKUP_DIR (mounted backup medium). The backup script optionally accepts GPG_PASSPHRASE_FILE for non-interactive use; otherwise the GPG agent prompts.

Audit trail. Every backup appends a single line to backup_log.txt in the format YYYY-MM-DD <sha256-hash> <filename>. Annual restore-tests are appended with a RESTORE-VERIFIED YYYY-MM-DD prefix. This log is the verifiable artefact of compliance with the Section 5 commitment and is reviewed on the cadence in Section 8.

6. Pre-made decisions

Three decisions made and signed off ahead of any incident, to remove the cost of deciding under duress.

6.1 Ransom payment policy

Decision: do not pay ransom. Reasoning: paying funds further attacks; ~50% of paying victims do not fully recover data; modern ransomware exfiltrates data so decryption does not undo the breach; OFAC sanctions risk; the cost of paying typically exceeds the cost of rebuilding for a small SaaS shop. If circumstances ever justify revisiting this decision, it requires written sign-off from the platform operator and legal counsel.

6.2 Breach declaration trigger

Trigger: any confirmed or strongly-suspected exfiltration of personal information triggers POPIA Section 22 notification within 72 hours. The 72-hour clock starts on suspicion, not confirmation. Personal information includes learner records, attempt scores, password hashes, session tokens, and any uploaded working sheet scans. The decision-maker is the platform operator (responsible party); legal counsel is consulted but the timeline does not pause for legal turnaround.

6.3 Communications fallback

If primary channels (email, Slack) are compromised or assumed compromised, incident communication moves to phone. A list of relevant phone numbers is maintained in the offline-stored DR plan: registrar support, Render support, legal counsel, business partner, key client contacts. A pre-drafted POPIA-aligned breach notification template is included in the same offline document.

7. Failover to a non-Render host

If Render becomes unsuitable due to cost (>5% of revenue), regional latency, sustained outage exceeding RTO, or a client demand for SA data residency, a documented procedure exists to migrate to a SA-region host (Hetzner SA, CloudAfrica, or equivalent).

PhaseEstimated duration
Provisioning + base setup4–8 hours
Database migration1–2 hours
App deployment under systemd4–6 hours
nginx + Let's Encrypt SSL2–3 hours
DNS swap + smoke testing1–2 hours (plus up to 48h DNS propagation)
Backup procedure setup2–4 hours
Total one-time effort14–25 hours focused work
This is a documented option, not the recommended path. Self-hosting transfers the burden of SSL certificate renewal, systemd process management, manual deployment pipelines, OS patching, and backup infrastructure to the platform operator. For a single-developer shop, this complexity dwarfs the FX-rate exposure on Render at small client counts. Stay on Render until a trigger condition is met.

The verification log is maintained in the administrator guide. A failed verification is treated as P1: backup integrity is foundational; everything else stands on it.

9. Paste-ready procurement responses

9.1 Free tier (current state — honest)

Backup & Recovery — current state The application is hosted on Render's free tier; the database is managed PostgreSQL hosted by Neon Inc. (neon.tech). Neon's free tier does not include automated snapshots or point-in-time recovery. The current backup approach is manual encrypted pg_dump taken before any schema migration. RPO is undefined; RTO is 2–8 hours from the last manual dump. Upgrade to paid tiers (Neon Launch for the database, Render paid for the application) with point-in-time recovery is a condition of any production cohort deployment, and a written upgrade procedure exists.

9.2 Paid tier (post-upgrade)

Backup & Recovery — paid tier The application runs on Render's paid tier (always-on, no cold starts). The database is Neon Launch managed PostgreSQL with daily automated snapshots and point-in-time recovery (PITR) to any second within the retention window. Manual snapshots are taken before any schema migration. A monthly encrypted off-platform backup (pg_dump stored outside both the Render and Neon accounts) provides a last-resort recovery path. RPO is 1 hour; RTO is 4 hours. Backup integrity is verified quarterly via test restore and annually via full tabletop exercise.

9.3 Ransomware-specific

Incident Response — ransomware A written ransomware response plan exists, stored offline (printed and on a USB outside the production cloud accounts). Pre-made decisions include: ransom payment policy (do not pay), breach declaration trigger keyed to POPIA Section 22 with a 72-hour notification clock starting on suspicion, and an offline communications fallback list. An annual tabletop exercise tests recovery end-to-end against the off-Render backup. The response procedure addresses account-takeover scenarios specific to a managed-PaaS context: GitHub, Render, and email account compromise as primary vectors.
