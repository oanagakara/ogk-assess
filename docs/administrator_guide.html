1. Platform overview

The assessment platform is a single-application Django system deployed on Render. Each client organisation gets its own deployment — one Render service per tenant. There is no shared database between clients.

The deployment model means:

  • Client A's learner data never mixes with Client B's.
  • Each deployment is configured by a single environment variable (TENANT_SLUG) that determines which branding record to load.
  • Updating branding (colours, logo, name) for a client requires only a database change — no redeploy.
  • Structural template changes require a file change and redeploy.
Architecture note: The platform reads the active Tenant record at startup and caches it in memory. The cache clears automatically whenever the Tenant record is saved in the admin.

2. Accessing the admin interface

The Django admin URL is configurable per deployment via the ADMIN_URL_PREFIX environment variable (default: _platform-admin). Your admin URL is:

https://<your-hostname>/<ADMIN_URL_PREFIX>/

Only superuser accounts can log in here. Assessors use /accounts/login/ instead.

Keep superuser credentials separate from assessor credentials. Superusers can modify any record including marks and scores.

3. First-time deployment on Render

Follow these steps every time you create a new Render service for a client. This covers the full sequence from deploy to a working, branded site.

1
Deploy the service
Push your code to GitHub. In the Render dashboard, create a new Web Service connected to your repository. Use the branch you want to deploy (typically main).
2
Bind a PostgreSQL database
In Render, create a new PostgreSQL instance and bind it to the service. Render automatically injects DATABASE_URL into the service's environment.
3
Set environment variables
In the service → Environment tab, add the following. Mark sensitive values as Secret (eye icon → lock).
VariableValueSecret?
DJANGO_SECRET_KEYGenerate: python -c "import secrets; print(secrets.token_urlsafe(50))"Yes
DEBUGFalseNo
ALLOWED_HOSTSYour Render hostname, e.g. myapp.onrender.com. No https://, no trailing slash. Add a custom domain here too if you have one, comma-separated.No
TENANT_SLUGThe slug of the Tenant record you will create in step 6. Example: defaultNo
DATABASE_URLAuto-injected by Render when you bind a database. Do not set manually.Yes
ADMIN_URL_PREFIXA hard-to-guess path segment, e.g. _mgmt-2026. Write this down — you will need it to access the admin.No
ANTHROPIC_API_KEYYour sk-ant-api03-… key. Required for AI marking.Yes
DJANGO_SUPERUSER_USERNAMEUsername for the initial superuser account.Yes
DJANGO_SUPERUSER_PASSWORDStrong password (12+ characters).Yes
DJANGO_SUPERUSER_EMAILYour email address.Yes
4
Wait for the deploy to complete
The build script (build.sh) runs collectstatic, migrate, and creates the superuser automatically on first deploy. Watch the Render Logs tab — a successful deploy ends with the gunicorn startup line.
5
Log in to the admin
Navigate to: 
https://<your-hostname>/<ADMIN_URL_PREFIX>/
Log in with the superuser credentials you set in step 3.
If you see a 500 error, check Render logs. The most common cause is ALLOWED_HOSTS not matching the hostname exactly.
6
Create the Tenant record
Admin → Tenants → Add tenant. At minimum, fill in:
  • Name — displayed in the sidebar, titles, and login page
  • Slug — must match TENANT_SLUG exactly (auto-filled from Name, verify it)
  • Is active — must be checked
All colour and logo fields are optional now and can be filled in later. Save the record.
Until the Tenant record exists, the site shows "Assessment" as the name. Everything else still works — branding is cosmetic.
7
Verify
Visit your deployment URL (not the admin path). Confirm:
  • The login page loads and shows your organisation name.
  • No 500 errors in the Render logs.
  • Log in as an assessor and create a test session end-to-end.
ALLOWED_HOSTS after a custom domain: If you later add a custom domain (e.g. assess.acme-training.co.za), add it to ALLOWED_HOSTS as a comma-separated value alongside the Render hostname and trigger a redeploy.

4. Onboarding a new client (tenant)

Full onboarding for a new client takes approximately 20 minutes once you have their branding assets.

1
Gather branding assets from the client
You need: logo (SVG preferred), logo on dark background (SVG), favicon (.ico), hex colour codes for primary/accent, organisation legal name, support email, footer text.
2
Decide a slug
Lowercase, hyphens only. Example: acme-training. This becomes the directory name for their assets and the TENANT_SLUG env var. Once set in production, do not change it — it would break file paths.
3
Add static assets to the repository
Create the directory static/tenants/<slug>/ and add: 
static/tenants/acme-training/
  logo.svg          ← header logo (colour version)
  logo-white.svg    ← header logo (white/reversed version)
  favicon.ico       ← browser tab icon
Commit and push. The files will be served via WhiteNoise after the next deploy.
4
Create the Tenant record in admin
Go to /admin/ → Tenants → Add tenant. Fill in all fields (see Section 4). Set Is active to checked. Save.
5
Create a new Render service
Fork or copy the existing Render service for the client. Set these environment variables (see Section 5): 
TENANT_SLUG=acme-training
DJANGO_SECRET_KEY=<generate a fresh key>
DATABASE_URL=<new PostgreSQL connection string>
DEBUG=False
6
Run migrations on the new deployment
In the Render shell for the new service: 
python manage.py migrate
python manage.py createsuperuser
Then recreate the Tenant record in the new deployment's database (step 4 above — each deployment has its own database).
7
Verify
Visit the new deployment URL. Confirm:
  • Client logo appears in the sidebar and login page.
  • Browser tab shows the client's favicon.
  • Page title shows the client name.
  • Login page heading shows the client name.
Default fallback: If TENANT_SLUG is not set, the system falls back to default. The default tenant should exist in every database as a safety net.

7. Managing users and assessors

User types

TypeAccessHow to create
SuperuserDjango admin + full assessor interfacepython manage.py createsuperuser
Staff assessorFull assessor interface including Questions viewAdmin → Users → Is staff = ✓
AssessorAssessor interface (no Questions)Admin → Users → assign to assessor group

Creating an assessor account

  1. Go to /admin/ → Users → Add user.
  2. Set a username and initial password. The assessor can change their password later.
  3. On the next screen, scroll to Groups and add the user to the assessor group. Or tick Staff status for full access.
  4. Save.
There is no self-registration. All assessor accounts must be created by an administrator.

Resetting a password

Go to /admin/ → Users → select the user → Password section → this form link → set new password → Save.

8. Assessment templates and questions

Assessment templates define the structure of an exam. Each template contains sections, and each section contains questions. Templates are shared across all sessions.

Question types

KindCodeDescription
TexttextFree-text response. Auto-marked if an answer key is set.
Fill in the blanksfill_blanksLearner fills gaps in a sentence. Auto-marked.
ReorderreorderDrag-to-reorder items. Auto-marked.
MatchingmatchMatch pairs. Auto-marked.
Multiple choicemcqSingle correct answer. Auto-marked.
Long divisionlong_divisionNumeric working. Auto-marked.

Questions marked is_active = False are hidden from learners during the exam. Staff assessors can toggle question active state from the Questions view in the assessor interface.

Answer keys

Answer keys are stored as JSON in the answer_key_json field. These drive auto-marking. Refer to the fixture files in assessment/fixtures/ for format examples per question type.

9. Running a session

Creating a session

  1. Log in as an assessor or staff user.
  2. Go to Sessions → New Session.
  3. Select the assessment template, set the seat limit, and create the session.
  4. The system generates an 8-character session code (e.g. AB3X7KP2).

Learner entry flow

  1. Learner navigates to /session/<code>/join/ on their machine.
  2. They enter their ID number. If they are a registered learner, their details pre-fill; otherwise they register on the spot.
  3. They proceed through the honesty declaration, instructions, and then the exam.

Session expiry

Sessions expire after 2 hours from creation. Learners already in an active attempt can still submit after the session expires — the timer on their screen governs their individual time. New learners cannot join an expired session.

Session monitor

From Sessions → click a session code → Monitor. The monitor page shows all active attempts in real time (auto-refreshes every 30 seconds). Use this during exam delivery to watch for learners who stall or go inactive.

10. Marking and results

Auto-marking

When a learner submits, all question types except LIT-D-WRITE (long-form writing) are auto-marked immediately. Auto-marked scores appear in the Marked tab.

Review queue

The Review Queue in the assessor sidebar shows only attempts that contain LIT-D-WRITE responses awaiting human review. Assessors score these manually using the rubric panel, then mark the response as reviewed.

Exporting results

From Results at a Glance, click Export CSV. The export includes learner demographics, scores per question, and totals.

The CSV export is restricted to staff users. Standard assessors see the results table but do not see the export button.

11. Template and branding overrides

Most branding changes (colours, name, logo, footer) require only a Tenant record update in admin — no code change or redeploy. The cache clears automatically on save.

For structural layout changes (e.g. adding a custom header element, different footer HTML), use the template override system:

  1. Create a directory at templates/tenants/<slug>/ in the repository.
  2. Copy only the template you need to change into that directory, preserving its path relative to the templates/ root.
    Example — to override the login page for client acme-training:
    templates/tenants/acme-training/registration/login.html
  3. Edit that copy. It can still use {{ tenant.* }} variables and extend other templates normally.
  4. Commit, push, and redeploy.

Django resolves templates in this order for the active tenant:

  1. templates/tenants/<active-slug>/ — client-specific override
  2. templates/tenants/default/ — platform default override
  3. templates/ — global templates
  4. App templates (assessment/templates/)

Custom CSS beyond colour variables

If a client needs styling that CSS variables cannot cover, drop a file at static/tenants/<slug>/custom.css. Add a link tag to the relevant base template override for that client. This is an escape hatch — use sparingly.

12. Troubleshooting

SymptomLikely causeFix
Sidebar shows "Assessment" instead of client name No active Tenant record in the database, or TENANT_SLUG does not match any slug Create or correct the Tenant record. Verify TENANT_SLUG env var matches exactly (case-sensitive).
Logo not appearing File not deployed, or logo_url path in Tenant record is wrong Confirm file exists at static/tenants/<slug>/logo.svg. Run python manage.py collectstatic if needed. Check the path in the Tenant record starts with /static/.
Branding change in admin not reflected on site Tenant cache not cleared (should happen automatically on save) Save the Tenant record again. If still stale, restart the Render service to force a cold start.
Learner cannot join session — "Session expired" Session is older than 2 hours Create a new session. Learners already mid-attempt are unaffected.
Auto-mark produced unexpected result Answer key JSON malformed or outdated Review answer_key_json for the question in admin. Refer to the Marking Rubric document for correct format.
500 error in production DEBUG=True is off (correct), so no detail is shown Check Render logs for the traceback. Common causes: missing migration (python manage.py migrate), missing DJANGO_SECRET_KEY, database unreachable.
Working sheet upload fails File too large or unsupported type Only PDF and image files are accepted. Check the file size — very large scans may exceed the request limit.

Checking the Render logs

In the Render dashboard → select the service → Logs tab. Filter by Error level first. Django logs unhandled exceptions with a full traceback here even when DEBUG=False.

Applying a database migration after a code update

If a deployment includes model changes, migrations must be applied manually after the deploy completes:

python manage.py migrate

Run this from the Render shell for the affected service. Render does not run migrations automatically.
