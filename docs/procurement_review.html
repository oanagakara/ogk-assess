What Passes

Core workflow assessment The core workflow is sound. Session creation → learner join → timed delivery → marking → results is complete and coherent. The auto-marking with partial marks and working detection is genuinely clever for the price point. The review queue with a badge count is the kind of thing that tells me someone thought about the actual job, not just the feature list. Working sheet upload-to-database sidesteps the hosting limitation cleanly — practical engineering.

What I Would Flag Before Signing

  1. 1. Single-developer risk There is no team, no bus factor mitigation, no documented succession. If the developer is unavailable for two weeks, there is no support path. I would require a clause in the contract and ideally an escrow arrangement for the source code.
  2. 2. Render free plan in production The platform cold-starts after inactivity — unacceptable for a timed examination environment. The first learner on a Monday morning could sit staring at a spinner for 30 seconds while the instance warms up. This must be on a paid plan before go-live with a real cohort.
  3. 3. ✓ Resolved — Data Processing Agreement A POPIA-compliant DPA has been produced covering responsible party and operator obligations, sub-operator disclosure (Render, GitHub), transborder flow acknowledgement, 72-hour breach notification, data subject rights procedure, audit rights, and retention periods specific to the categories of personal information the Platform actually processes. Schedule C documents the technical and organisational security measures in place. The document requires the parties' signatures before it becomes operative — that is not a deficiency in the document, it is how agreements work. The flag is closed pending execution.
  4. 4. No backup strategy documented PostgreSQL on Render. What is the recovery point objective if the database is corrupted or the provider has an outage? "Managed PostgreSQL" is not a backup strategy — it is a hosting arrangement.
  5. 5. No mobile consideration The specification states "optimised for 1280px+". In a supervised lab this is acceptable. But some campuses use tablets or mixed hardware. Not a blocker, but the constraint must be understood and documented before deployment.
  6. 6. Reporting friction The CSV-only default will last approximately 90 days before someone at head office asks for a management report. That conversation will be easier — and cheaper — if the dashboard add-on pricing is agreed at signing rather than raised as a change request later.
  7. 7. ✓ Resolved — Score audit log Adequate. Every score write is recorded — question, action, mode, before and after, who touched it. The trail is printable. This is what I asked for and it has been delivered without being asked twice, which is not nothing. I note that it should have been there from the start; its absence in v1 was a compliance gap, not a feature request. The flag is closed.
Verdict — Conditionally Recommend for Pilot Six flags raised. Two closed. The developer is moving through the compliance list without being chased, which is the correct disposition. Four remain open. The pre-conditions for live deployment are now reduced to:
  • Upgrade to paid hosting tier (non-negotiable for a timed examination environment)
  • Execute the Data Processing Agreement — the document exists, the signatures do not
  • Written support SLA with escalation contacts and response time commitments
This remains a conditional approval. The conditions remain, though the list is shorter.
