## Open

### [Manager — during review] `_attempt_expires_at()` vs `_expire_overdue_attempts()` use different duration sources
**Found while verifying:** Agent 2's extended-time accommodation work.
**What:** `_attempt_expires_at()` (learner.py) computes the overall-attempt deadline from the hardcoded `ASSESSMENT_DURATION` constant (2 hours). `_expire_overdue_attempts()` (_common.py) computes it from `_template_total_duration(template)` — the real, summed duration of that specific template's sections. For the real production templates these currently agree (60+60min sections = 2hrs), so it's never surfaced. For a template with a different total (e.g. a single 60-min section, as used in the new accommodation tests), they diverge — the constant-based check doesn't fire when the template-duration-based one would.
**Why it's a blocker, not something to silently fix:** this predates today's work entirely — not introduced by any Phase B agent. Reconciling it (making `_attempt_expires_at` use `_template_total_duration` instead of the constant) is a real behavior change to core timing logic, not an accessibility fix, and deserves a deliberate decision rather than a silent patch bundled into this remediation.
**What was done in the meantime:** the two affected tests in `test_extended_time_accommodation.py` were rewritten to exercise section-level expiry (`_section_expires_at`, which correctly uses each section's real duration and is not affected by this inconsistency) instead of overall-attempt expiry, so Agent 2's actual scope (multiplier threading) is still fully verified. The underlying constant-vs-template-duration inconsistency itself is untouched.

### [Agent 4 — Tier 2 badge/contrast audit] `badge-error` fails WCAG AA 4.5:1 in the `business` DaisyUI theme; requires a Tailwind/DaisyUI rebuild, not a template fix
**Found while:** auditing badge/status-color contrast per the roadmap's Tier 2 item ("Badge/status color contrast unverified").
**What:** computed exact sRGB values from the compiled `static/css/output.css` OKLCH theme tokens for both themes this app ships (`business` — dark, the default; `corporate` — light, user-toggleable via the header theme switch in `base.html`). `.badge-error`'s text/background pair (`--erc` on `--er`) is:
- `corporate` theme: `#000000` on `#ff5861` → 6.83:1 — **passes**.
- `business` theme (the default theme, and what most learners will see unless they toggle): `#f2d8d4` on `#ac3e31` → **4.469:1 — fails** the 4.5:1 AA threshold for normal text by a small margin (this is 16px/`text-base` timer text, not large text, so the 3:1 large-text allowance doesn't apply). Full-precision calc: text rgb(242.07, 216.36, 211.8) on bg rgb(172, 62, 49).
- `.badge-warning` passes comfortably in both themes (9.51:1 business, 12.62:1 corporate). `.badge-outline` (the default/idle timer state, `color:currentColor` inheriting the card's body-text color) passes very comfortably in both themes (10.26:1 business, 20.33:1 corporate) — my earlier assumption that outline text inherited the warning/error hue was wrong; it inherits `--bc` (base content), so that state was never actually at risk.
**Where it's used:** `question.html`'s `.section-clock` badges (final-10-seconds state) and `review_question.html`'s `#review-countdown` badge (same final-10-seconds state) — both in my scope, both now already carry a non-color signal too (warning-triangle icon + `aria-live` text announcement, see Logged judgement calls below), so the *information* isn't color-only anymore even with this contrast shortfall outstanding. But the visual contrast failure itself is real and independent of that fix.
**Why it's a blocker, not something to silently fix:** `--er`/`--erc` are DaisyUI's built-in `business` theme tokens (`tailwind.config.js` just lists `business` as one of the four enabled themes — the palette itself isn't overridden anywhere in this repo). There is no already-compiled alternate class combination that fixes it — I checked `badge-outline.badge-error` (text=`--er` on card bg) as a candidate substitute and it's worse (2.71:1). Fixing this for real means either (a) a Tailwind/DaisyUI rebuild with a theme override for `--erc` (or a custom `wac`-style safelisted color), or (b) an inline `style=` hardcoded hex override on just these two badges, which would silently diverge from the theme system and isn't a "utility class already in the compiled output" the task scope allows me to reach for. Per this task's explicit constraint, logging rather than doing either.
**What was done in the meantime:** nothing changed about the badge's color itself. The urgency signal was made non-color-dependent (icon + live-region text), which addresses the WCAG 1.4.1 "use of color" finding from the roadmap even though the separate 1.4.3/1.4.11 contrast-ratio finding on `badge-error` in the `business` theme remains open.
**Suggested next step for whoever picks this up:** smallest fix is probably a one-line DaisyUI theme override (`daisyui.themes` config supports per-theme color overrides) bumping `business`'s `--erc` lightness slightly, verified against the same 4.5:1 target — but that touches the theme for every `badge-error`/`btn-error`/etc. app-wide, not just the timer, so it needs sign-off and a full rebuild + visual pass, not a scoped template edit.

## Logged judgement calls (Tier 2 — consent modal focus/ARIA, `session_join.html` + `details.html`)

**Agent:** Tier 2 consent-modal focus/ARIA remediation agent (worktree `agent-a6b188a26919673a1`).

These were in-scope decisions the task explicitly asked to be logged rather than guessed silently. None are blocking — implemented with the most conservative option in each case.

1. **Escape key is fully suppressed (not just re-focused into the modal).** These consent dialogs have no cancel/decline affordance anywhere in the UI — the only paths forward are scrolling to the end and clicking "I accept," or leaving the page/tab entirely. There is nowhere meaningful for Escape to send the learner, and letting it close the `<dialog>` would strand them on a page with no way to reopen it except the "Open consent agreement" button, which only exists in the pre-consent render state, not after the dialog is already showing. Rather than build new "decline" UX (out of scope — that's a consent-flow logic change), I `preventDefault()` the dialog's native `cancel` event so Escape is a no-op while the modal is open. If product wants an explicit "I do not consent" exit path, that's a decision for whoever owns `HonestyForm`/the consent flow, not this Tier 2 ticket.

2. **Focus trap implementation is a hand-rolled Tab/Shift-Tab cycle**, not a library (no focus-trap dependency exists in this codebase and adding one felt like scope creep for a 2-dialog fix). It recomputes the focusable-element list on every Tab press (cheap, small DOM) so it stays correct as the Accept button transitions from `disabled` to enabled mid-session. `#consent-scroll` is included in the boundary list even though it carries `tabindex="-1"` (deliberately excluded from normal Tab order) because it's still the modal's initial-focus landing spot and needs to count as a valid trap boundary.

3. **Scroll-gate unlock announcement uses both an `aria-live="polite"` region AND moves focus to the newly-enabled Accept button.** Belt-and-braces: the live region announces the state change for anyone not already focused on the button; the focus move gives keyboard users an immediate, unambiguous "you can act now" without requiring them to go find the button. This double signal was a judgement call — a single mechanism (just the live region, or just the focus move) felt less certain to work reliably across screen reader/browser combinations, and the modal has no other focusable content between the sentinel and the button, so moving focus there doesn't skip anything a learner still needs to read.

No new accessibility issues were discovered outside the stated scope during this work. `question.html`, timer code, and match/long-division question types were not touched.

## Logged judgement calls (Tier 2 timer live-region + badge contrast, Tier 3 fixes — Agent 4)

**Agent:** Agent 4, working directly on `accessibility/wcag-2.1-aa-remediation` (no worktree). Scope: countdown timer accessibility, badge/contrast audit, ~12 Tier 3 items, per the roadmap.

1. **Timer live-region announces on a fixed schedule, not every second.** Making the visible countdown badge itself an `aria-live` region (or announcing every `tick()`) would re-announce every second — unusable and actively hostile to screen reader users during a 45-60 minute section. Instead I added a separate visually-hidden `#section-timer-live` / `#review-timer-live` region (same sr-only CSS pattern Agent 3 already established for `#consent-live-region` in `details.html`/`session_join.html`) and only push a new announcement at a fixed list of thresholds (hour/half-hour/quarter-hour marks tapering down to every second in the final 5 seconds, mirroring how the visual badge escalates outline→warning→error). `role="status"` + `aria-live="polite"` throughout — never `assertive` — because losing time is not itself an emergency requiring interruption; the visual+textual warning states carry the urgency instead.

2. **Non-color urgency signal is an `aria-hidden` warning-triangle icon (reused from `details.html`'s existing warning-banner icon, same path data) plus text prefixes ("Time warning:" / "Time critical:") in the live-region announcement — not a change to the visible badge text itself.** Considered prefixing the visible on-screen countdown text too (e.g. "⚠ 00:45") but that would shift the badge's width/layout at exactly the moment learners are already stressed about time, and duplicates what the icon already communicates visually for sighted users. The icon is `hidden` by default and only unhidden when the badge crosses into `badge-warning`, so it appears/disappears in lockstep with the color change — same trigger, non-color-dependent signal.

3. **`badge-error` contrast failure (business theme, 4.469:1) logged as a blocker, not patched with an inline style.** See the Open blocker entry above. Considered a scoped inline `style="color:...;background-color:..."` override on just the two `badge-error` usages I touched, but that would (a) diverge those two badges from the theme system so they'd stop responding to the corporate/business toggle correctly, and (b) is exactly the "invent a new color combination outside the compiled output" move the task told me to avoid and log instead. Left the class as-is.

4. **Heading hierarchy swap in the `passage_split` layout (`question.html` and `review_question.html`): "Reading text" promoted from `<h2>`/plain heading to `<h1>`, "Question N of total" demoted from `<h1>` to `<h2>`.** The original DOM order had an `<h2>` (passage panel) appear before an `<h1>` (question panel) — a real hierarchy violation (h2 before the page's first h1). Two ways to fix it: (a) keep "Question N" as the page's `<h1>` and move it earlier in DOM order than the passage panel, which would mean restructuring the two-column grid markup, a bigger and riskier change to layout Agent 1 already redesigned around for match/long-division keyboard access; or (b) just swap which panel carries `<h1>` vs `<h2>`, keeping DOM order as-is. I chose (b) — it's a pure heading-level swap, zero layout/DOM-order/CSS change (`card-title` styling is class-driven, not tag-driven, confirmed against `output.css`), and it matches the visual reading order (passage is the left/first column, question is the right/second column) to the semantic heading order. Applied identically in both `question.html`'s `passage_split` branch and `review_question.html`'s `passage_split` branch for consistency. Did not touch the match-widget's `<h3>` ("Words") or the `mcq`/`writing`/`form_fill` branches' structure — those were already correctly nested under their respective `<h2>` question headings with no skipped levels.

5. **Form-fill/text-answer "Your answer" label was previously a single label shared across all four answer-type branches (form_fill, mcq, writing, plain text), rendered once before the branching `{% if %}` — meaning it was visually followed by an unrelated per-field label in the form_fill case, and had no `for=` pointing at anything since three of the four branches don't have a matching single input.** Moved the label inside each branch instead of sharing one copy: form_fill gets no shared label at all (each field already has its own, now with `for="id_ff_{name}"` matched to a new `id` on its input); mcq keeps a bare group label (no `for=`, since it's a label for the whole radio group, not one input — each option already has correct implicit `<label><input></label>` wrapping); writing and the plain-text fallback each get `for="id_answer"` matched to a new `id="id_answer"` on the textarea / Django's existing `id_answer` on `form.answer`. This is a structural cleanup beyond a pure `for=` add, so flagging the judgement call — the alternative (leave the shared label in place and only bolt `for=` onto it, pointing at whichever input happens to exist per-branch) would have produced a label pointing at nothing in the form_fill/mcq branches, which felt like a fake fix rather than a real one.

6. **`base.html` header controls (font picker `<select>`, zoom in/out buttons, theme toggle) given `aria-label`s.** Not named explicitly in the roadmap's Tier 3 examples, but falls squarely in the "labeling/ARIA" category the roadmap describes, appears on every learner-facing page (shared via `{% block body %}`), and wasn't touched by Agents 1-3. Zoom buttons already had `title=` attributes — added `aria-label` alongside rather than relying on `title` alone, since `title` support for accessible-name computation is inconsistent across screen readers/browsers and isn't a reliable substitute. Also marked the four decorative SVG icons in that header row `aria-hidden="true"` (font glyph, sun/moon theme icons) since they carry no information beyond what the new `aria-label`s already state.

7. **`role="alert"` added to the two (byte-identical, duplicated per layout branch) `form.answer.errors` validation-message divs in `question.html`.** These are server-rendered at page load, already in the DOM (not injected later), so `aria-live` wouldn't reliably fire for them on first render in every screen reader — `role="alert"` is the correct WCAG 4.1.3 status-messages construct for content that's just been added/is present at load and needs immediate attention regardless of live-region mutation timing.

No new out-of-scope accessibility issues were discovered beyond the `badge-error` contrast finding logged above. `session_join.html`, `details.html`, the match/long-division widget interaction logic, and the extended-time accommodation code were not touched — only the countdown-timer markup/JS, badge markup, heading levels, and label/ARIA attributes described above.
