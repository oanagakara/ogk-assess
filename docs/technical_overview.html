1. Executive Summary

The platform assesses learners aged 18–29 against NQF levels 1–4 for learnership placement, including learners with physical, neurological, or psychiatric disabilities. It is a Django 6 / Python 3.13 application backed by managed PostgreSQL, deployed one tenant per Render service so that no client’s data shares a database with another. POPIA compliance is documented in a signed Data Processing Agreement; an independent security audit (21 April 2026) found no critical vulnerabilities, and the three HIGH-severity findings raised at that audit have been remediated in code. Backup, recovery point/time objectives, and ransomware response are documented in a standalone Disaster Recovery Plan. Support is contracted under a Service Agreement with response-time commitments. This document summarises each topic and points to the underlying artefact for depth.

4. Security Posture

An independent security audit was conducted on 21 April 2026 against the OWASP Top 10 plus Django-specific hardening guidance. The audit found no critical vulnerabilities. It identified three HIGH-severity, four MEDIUM-severity, and three LOW-severity findings, alongside seventeen positively-verified controls.

Controls verified at audit (selection)

Verified passing SECRET_KEY loaded from environment with hard-fail in production; HTTPS enforcement (SECURE_SSL_REDIRECT, HSTS); CSRF and session protection; Content-Security-Policy and Permissions-Policy headers; brute-force rate limiting on login (10 attempts / 10 min); session-bound assessment access; login_required + @user_passes_test on every assessor view; magic-byte file-type validation on uploaded scans; opaque non-enumerable identifiers; custom error pages (no debug info leakage); immutable score audit log.

HIGH-severity findings — remediated in code (re-audit pending)

6. Backup & Disaster Recovery

Disaster recovery is documented as a standalone plan covering five scenarios: corrupted database, accidental deletion, full-region outage, account-level provider compromise, and source code repository compromise. Recovery objectives are tier-dependent.

Current state (free tier)Target state (paid tier — before first cohort)
RPO (data loss tolerance)Undefined — manual pg_dump only1 hour via point-in-time recovery
RTO (recovery time)2–8 hours from a recent dump4 hours — snapshot restore plus smoke test plus notification
Backup automationNone on free tierDaily snapshots plus PITR plus monthly off-Render encrypted dump
Backup verificationManual on demandQuarterly restore test plus annual full tabletop exercise

Off-Render backup commitment

A monthly pg_dump is downloaded out of the Render account, encrypted with AES-256 (GnuPG symmetric), and stored on a separate medium with separate credentials. Twelve monthly backups are retained on rolling rotation. This addresses the scenario where the Render account itself is compromised and Render-side snapshots become untrusted — an outcome that account-level credentials alone cannot recover from.

Failover commitment

A documented procedure exists to migrate from Render to a South African host (Hetzner SA / CloudAfrica) within an estimated 14–25 hours of focused work. This is held as a contingency, not a default operating mode.

See Disaster Recovery Plan in the Annex.

8. Continuity & Key-Person Risk

Group IT will rightly note that OANAGAKARA is presently a single-developer operation. The procurement self-review flagged this and we want to address it transparently rather than minimise it.

  • Source code escrow / handover. The full source repository, deployment configuration, administrator guide, and operational runbooks can be placed in escrow with a nominated third party on contract execution. On a defined trigger event (extended unavailability, business cessation), the Responsible Party receives the escrow release and continues operating the platform on its own infrastructure under the existing licence terms.
  • Operational runbook. Deployment, tenant onboarding, environment variables, role management, troubleshooting, and migration procedures are documented in the Administrator Guide. A reasonably competent Django operator can stand up and run the platform from this document alone.
  • Stack choice. The technology choices (Django, PostgreSQL, server-side rendering, no proprietary framework) were made to keep the platform portable and the operator pool large.
  • Insurance and continuity. Director’s professional indemnity and cyber liability cover will be in place by first paying-cohort go-live; specifics available to Group IT on request.
